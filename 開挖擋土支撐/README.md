# 擋土支撐計算網頁工具 v1

以 `2_開挖擋土支撐-v95000.xlsm`、既有分析輸出與計算書工作流為基礎，建立的單機本地版 web 工具。
目前版本已包含：

- `FastAPI + SQLite + 本地專案資料夾` 的後端骨架
- `.RIO / .LST / .o` 分析文字檔匯入 parser
- Excel `Fa / Fbx / Fby / LdaB / LdaC / Ratio` 對應的計算核心
- 支撐、橫擋、斜撐、大角撐、柱構件的檢核流程
- 匯入支撐／斜撐的安裝、控制內力、拆撐時序與實際施工步驟明確對應
- 拆撐後荷重處置、承接構造或另案檢核邊界的人工指定與封閉驗證
- ERH 重撐／回撐列的 H 型鋼無偏心純軸壓容量實算、RSC 證據 JSON 與 RVR 受限範圍回填
- 覆工板控制軸力至固定共構柱 ID 的驗證式多施工階段交接與包絡
- React + TypeScript 單頁 workflow 介面
- RVR 組織 Ed25519 加密建鑰、公開 RKE 登錄包、輪替關聯、獨立核身確認、串接指紋撤銷事件，以及只含公開資料的信任清冊備份／受控復原
- 五類補充證據範本的本機核准治理，以及共用 RKE 信任清冊的離線組織簽章發布包
- RVR 離線備份週期、30 天新鮮度門檻、隔離暫存復原演練與 `RDR-...` 通過收據
- PDF／Word 計算書輸出：預設為可列印的內部審閱，明確勾選核可後才標示為正式附件；核可 PDF 同步建立逐頁像素、OCR 與文字層對齊證據
- 後端基礎單元測試
- `excavation-traceability.catalog.json` 規範語意追蹤與 contract test

## 專案結構

- `backend/app`: API、專案儲存、Excel 參考資料載入、parser、計算與報表
- `backend/tests`: parser 與計算 smoke tests
- `frontend`: React + Vite 前端
- `app_data`: 執行後自動建立，存放 SQLite、專案 JSON、匯入檔與 PDF 報表

本機工程案例、`.LST/.o/.i` 分析檔、Word/PDF 輸出與 Excel 參考活頁簿不隨程式碼提交；若要完整使用 Excel 參考資料，請在本機放置 `2_開挖擋土支撐-v95000.xlsm`。

## 啟動方式

### HTML 模式

直接建置前端並由後端提供靜態 HTML 頁面：

```powershell
.\start_html_mode.ps1
```

啟動完成後，開啟 `http://127.0.0.1:8000` 即可使用。

停止服務：

```powershell
.\stop_html_mode.ps1
```

### 1. 安裝後端套件

```powershell
C:\Users\USER\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe -m pip install -r backend\requirements.txt
```

### 2. 啟動後端 API

```powershell
C:\Users\USER\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe -m uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8000
```

### 3. 啟動前端開發伺服器

```powershell
cd frontend
npm install
npm run dev
```

開啟 `http://127.0.0.1:5173` 即可使用。

尚無組織簽章金鑰時，可雙擊 `建立RVR組織簽章金鑰.bat`，在簽署單位本機產出密碼加密私鑰及可交付信任清冊管理者的公開 RKE 登錄包；同一組 Ed25519 金鑰與信任清冊可用於 RVR 及 SEV 身分簽章。私鑰不得送入網頁或交付其他單位；RKE 的持有證明不取代組織身分核對。撤銷必須記錄原因、處理者與選用的事故編號，並寫入不可由畫面覆寫的 `RVE-...` 串接事件清冊。完整程序見 `RECEIVER_KEY_MANAGEMENT.md`。

補充證據範本庫可先從接收端助手匯出，再雙擊 `簽署補充證據範本包.bat`，用同一套 Ed25519 私鑰離線建立組織簽章包。接收端的「匯入組織簽章包」會重算範本庫／封包指紋、驗證簽章並依本機 RKE 信任清冊分類；簽章只證明發布來源與傳遞完整性，所有匯入範本仍固定為待本機核准。完整程序見 `RECEIVER_EVIDENCE_TEMPLATES.md`。

信任清冊可從助手下載含 `RTB-...` 備份指紋與 `RTR-...` 清冊指紋的公開資料備份。匯入只先驗證及預覽差異；明確核准後才會建立復原前保護副本並置換清冊。有效清冊僅接受事件鏈向前延伸，舊備份不得移除 Key ID、改寫歷史或逆轉撤銷。此治理資料不會進入 PDF／DOCX 計算書。

定期作業可執行 `backup_receiver_trust_registry.ps1 -Mode Cycle -OutputDirectory <受控備份目錄>`。流程會建立並回讀驗證備份，再於隔離暫存清冊完成真實復原，確認正式清冊 SHA-256 未變動後產生 `RDR-...` 演練收據；不覆寫、不自動刪除歷史檔案，也不修改正式清冊。

## 計算書文件狀態

「報表匯出」頁的 PDF 與 Word 採相同文件狀態規則：未勾選核可時輸出 `文件狀態：內部審閱`，仍可下載與列印；勾選「核可為正式附件」後，輸出才改為 `文件狀態：正式附件`，並記錄產出工具、工具版本、輸出時間、核可時間與計算指紋。核可是這一次輸出的文件身分，不代表工程結果一定為 OK，也不取代設計者對計算內容的複核；切換案件、修改案件識別資料或變更計算輸入後，既有下載連結及核可勾選會清除，下一份輸出回到內部審閱。

核可 PDF 產生時，後端會實際渲染每一頁，以 RapidOCR 與 PDF 文字層做正規化 bigram 對齊，並將頁面像素範圍、兩側文字 SHA-256 與最低一致率寫入同名 `.canonical-render.evidence.json`。任一頁缺少可讀文字、沒有墨量、對齊低於 `0.50`，或 PDF 在驗證期間改變，都不會回傳可用的正式 PDF。此步驟通常比內部審閱 PDF 慢；畫面會在完成後提供單一 `.formal-source.zip`，並保留 PDF 與證據的個別下載。ZIP 採原子建立、回讀精確檔案清單與 bytes，且只含同次 PDF 與證據；可直接拖到 repo 根目錄的 `啟動案件附件工作台.bat`，工作台只做唯讀辨識並建議正式附件包管理器的來源模式。使用者點擊建議後，管理器才會驗證同名兩檔、大小與根目錄清單，再於隔離暫存區安全讀取並自動清理；此路徑不會自動建立附件包。ZIP 只是搬運用的「組包來源套件」，不是正式附件包，也不得直接附入主報告。組包器會自行重算證據並把 JSON 移到 `99_內部追溯_勿附入主報告/來源資料/`，不會把它列為附件正文。`latest-report.pdf` 只供快速取得最新副本；自動組包應使用畫面本次產出的來源套件或原始 PDF／證據配對。

工程名稱、計畫編號、委託單位、設計人員、校核人員與工程位置可留空；空白不會把文件判為 NG、DRAFT 或禁止核可，必要識別資料可由主報告或附件包承接。計算書只保留採用資料、計算／檢核過程、工程結果與精簡追溯欄位；操作提醒、待辦與證據鏈治理說明只留在 HTML 工作頁或內部 JSON，不寫入 PDF／DOCX 正文。

## 匯入覆工板施工階段荷重

覆工板的 `PuMax` 不會自動加到所有柱。請先用 `../結構工具箱/tools/建立覆工板施工階段荷重交接檔.bat` 將各施工配置的完整覆工板 JSON 轉成受控交接檔，再於實際承受覆工板反力的「一般共構柱」或「吊車位置共構柱」卡片按「新增覆工板施工階段」。每支柱都有固定 `column_id`；交接資料會綁定該柱，最多可保存 20 個具唯一名稱、階段 ID 與來源指紋的施工階段，也可在頁面重新命名或移除。

前端會驗證 schema、目標種類、單位、來源計算指紋、`CSH-` 交接指紋及「必須明確採用、不得自動套用」邊界；後端不信任前端摘要，會再次重算 `CSH-`，核對控制軸力、來源欄位、目標柱 ID、重複階段及重複來源。來源控制軸力保持原值；本柱採用 `Np = 來源控制軸力 × 反力分配比例`。同一交接指紋在所有啟用柱位的比例合計必須為 100%；分配至多根柱時，每柱都須填寫反力分配依據且使用相同施工階段名稱，否則全部相關柱位失敗關閉。單柱採用維持預設 100%，舊案不需補填分配資料。覆工板來源只證明軸力，不自行推定開挖柱座標方向；如施工配置存在額外傳力偏心，須在對應階段勾選「明確採用本階段附加傳力偏心」，輸入帶正負號的 `Δex / Δey` 與採用依據。後端依 `ΔMx = Np × Δex`、`ΔMy = Np × Δey` 與既有柱彎矩帶正負號組合，彎曲應力使用最終彎矩絕對值。未勾選卻夾帶非零偏心、已勾選但偏心均為零或缺少採用依據時均失敗關閉。

每一階段均以 `N = Np + N1 + N2 + N3 + N4` 完整重算，並強制加入「無施工構台荷重基準案」；柱互制、基礎壓入及基礎拉拔分別取其最不利控制階段，PDF / DOCX 計算書列出來源控制軸力、分配比例與依據、本柱採用軸力、附加偏心、`ΔMx / ΔMy`、最終 `Mx / My`、三種控制階段及精簡來源追溯。中間柱、柱位不符、缺少原始交接記錄、指紋不符、控制軸力不一致、分配不完整、重複來源或追溯欄位不完整時均失敗關閉。舊案只有單一 `construction_stage_load_t` 時會自動移轉成一個 100% 分配且不採用附加偏心的可追溯階段，維持既有專案相容性。

固定柱位、跨柱比例合計封閉檢查、多階段包絡及逐階段附加偏心解決的是「資料不誤套、不重複計入」及「各已匯入配置按明確採用值逐案取最不利結果」；哪一支柱實際承受反力、各柱比例的工程正確性、偏心座標正負方向、支撐內力變化及臨時傳力路徑，仍須依施工配置與正式分析人工判定。

## 匯入分析階段與施工步驟對應

外部分析檔的支撐或斜撐會分別保存安裝階段、各有效施工階段的軸力時序、控制內力階段及可辨識的拆撐階段；`.o` 包絡摘要的逐階段數值與並列控制階段會結構化保存，不再把單一包絡值複製成多階段資料，也不會誤把 BUT 設置階段當成控制內力階段。後端會以每一施工階段的軸力重新計算支撐或斜撐需求比，再以需求比取真正的控制階段；斜撐採用外部分析階段軸力原值，畫面上的線載重只作對應一致性驗證，避免小數捨入改變正式檢核。匯入列必須填寫實際施工步驟與階段對應依據，並勾選確認時序相符；若已辨識拆撐事件，還必須人工選擇「另案檢核、樓版、重撐／回撐、永久結構或其他」荷重處置，填寫承接構造（另案檢核除外）、傳力方向／作用線與正式依據，並另行確認承接構造檢核邊界。階段軸力為負值或非有限值、未確認、未指定拆撐處置、未填傳力方向、施工階段重複、控制階段不是最大包絡值、採用內力不一致、控制早於安裝，或拆撐未晚於控制時，後端一律以「資料未完整」拒絕完成檢核。舊匯入列若缺少安裝階段須重新匯入；既有已確認拆撐列須補填傳力方向後再計算，手動輸入列不受影響。

PDF／DOCX 計算書只列已採用的內力來源、安裝／控制／拆撐階段、實際施工步驟、對應依據、施工階段軸力時序與需求比包絡、需求比控制階段、承接設計需求、逐一承接對象的比例／分配需求／傳力方向及已確認的拆撐後荷重處置；尚未指定、未確認、重新套用等操作提示只留在 HTML 工作頁。這些欄位建立可計量、可追溯的交接起點，不會自行宣稱方向或比例採用正確。除接收端助手另列的 H 型鋼無偏心純軸壓重撐容量外，本工具不計算樓版、永久結構或其他承接構造；即使完成該軸壓實算，也不宣稱接頭、承壓、基礎／樓版或施工程序已通過，其容量適用性、偏心與實際傳力路徑仍須由設計者依正式模型、施工順序圖與專案文件另案驗證。

完成最新計算後，可在「報表匯出」頁一鍵建立 `excavation-removal-transfer-handoff` JSON。單一拆撐來源預設由主承接對象承擔 100%，也可新增最多 9 筆其他承接對象；每筆分別填寫處置種類、對象、方向、比例與依據，比例均須大於 0% 且合計 100%，同一對象與方向不得重複。後端會重新計算並只納入來源構件非 NG、生命週期完整且已確認拆撐處置的列；ERH v4 依承接對象拆成獨立 `ERT-`，分開列示來源控制軸力、構件設計軸力、分配比例及分配後承接需求，並以受控契約要求新產出的 RVR v5 結構化回簽驗算範圍與五類補充查核。舊 ERH v1／v2／v3 及 RVR v1／v2／v3／v4 仍可驗證。已發 ERH 版本會保存於專案，相同工程內容重複匯出時沿用同一版本，避免回簽失去對照基準。所有交接列固定從 `pending` 開始，且不得自動套用或自動標示為承接構造已驗證。

樓版、重撐、永久結構或其他接收端完成方向、分配、偏心、載重組合及容量檢核後，可在獨立「接收端回簽助手」匯入 ERH、填寫回簽單位、接收端採用需求、正式文件所核定的承載力與逐列結論，並由後端以受控欄位、自動彙整、固定責任邊界及指紋產生 `receiver-capacity-verification-receipt` JSON；同一頁也可用 ERH 檢查既有 RVR。對 `receiver.mode=reshore` 的列，助手另提供 H 型鋼無偏心純軸壓實算：依 X／Y 向 `KL/r`、`KL/r ≤ 200`、翼板及腹板局部細長限制與第六章容許軸壓應力，計算單支容量、支數不均勻後需求及可移轉容量。使用者必須填寫控制載重組合、有效長度與分配依據並確認無偏心；採 1.25 提高係數或另加軸力時另須填正式依據。結果會下載精確 bytes 的 `RSC-...` JSON 並回填檔名、SHA-256、軸力／穩定範圍及容量，但「其他檢核」固定保持未完成；長細比或局部細長不適用時可採用容量歸零。若要把整列改為通過，必須改以另含接頭、上下端承壓、底座／基礎或樓版、實際側撐、施工順序與預壓等查核的正式文件作為證據，不能只用 RSC。

RVR v2 起固定由後端計算「容量利用率＝採用需求／核定承載力」，RVR v3 再要求逐 ERT 記錄承載力文件編號、版次、日期、頁碼／章節、純檔名與小寫 SHA-256，RVR v4 增加正式模型、控制組合、傳力、偏心與極限狀態。新產出的 RVR v5 再把接頭與接合、端部與局部承壓、基礎／樓版或承接主體、側向支撐與有效長度、施工順序／預載與卸載控制分成五類；每類必須明列 `passed`、`failed` 或 `not-applicable` 及依據，`passed` 必須連結實際證據檔，其他檢核彙整由後端自動推導。RSC 純軸壓證據若與補充查核引用同一檔案，不能讓補充查核通過。來源端 SEV v2 會依 ERT 與證據種類逐檔重算 SHA-256，完整涵蓋 RVR 引用的主承載力及補充證據；檔案內容不會上傳、嵌入 RVR／SEV 或寫入專案。舊 RVR v1 至 v4 與 SEV v1 維持讀取相容。結構化欄位、雜湊與簽章只提供完整性及責任鏈，不取代工程內容審閱或正式核可；回簽資料也不會插入 PDF／DOCX 計算書正文。簽章合約詳見 `RECEIVER_IDENTITY_SIGNATURE.md`。

五類補充查核可將常用的查核依據、文件編號、版次、日期及頁碼保存為本機受控範本，並可匯出／匯入 JSON、以既有 Ed25519 組織金鑰離線簽署發布，或批次套用至全部同類交接列。schema v3 會保存內容版號、逐版變更欄位、本機審核人、核准時間、有效期限，以及簽章包匯入當下的發布來源；只有已核准且未過期的範本可用，內容修訂會自動升版、撤銷核准並清除原發布來源，任何外部匯入與舊 v1／v2 範本則一律回到待本機核准。發布簽章只證明來源與完整性，不證明工程內容或適用性。範本刻意排除證據檔名與 SHA-256；套用後仍須逐列重新選取本案實際檔案，不能以範本繞過 RVR v5 或 SEV v2 的逐檔核對。格式與操作詳見 `RECEIVER_EVIDENCE_TEMPLATES.md`。

來源端匯入 RVR v3 以上版本後，須在「報表匯出／拆撐承接構造驗證交接」逐 ERT 選取實際收到的證據檔。瀏覽器會重新計算 SHA-256 並與 RVR 記錄值比對；未全數相符且尚無有效 SEV 時，交接總狀態固定顯示「證據檔待逐列比對」，不得視為證據核對完成。SHA-256 相符但檔名不同時會保留警示，因檔名不是密碼學識別。未保存的當次比對狀態會在頁面重載、切換專案或切換 RVR 後清除；全數相符後，可填寫核驗單位、人員、角色與依據，由後端建立帶 `SEV-` 指紋的 `source-capacity-evidence-verification-record`，保存至專案並同步下載 JSON。SEV 固定連結來源計算、ERH、RVR、全部 ERT 的預期／實際 SHA-256、核驗時間與責任資訊，且重新開啟專案後仍可追溯；證據檔本身不會上傳或嵌入。SEV 可再下載 `SSR-` 離線身分簽署請求，雙擊 `簽署SEV身分請求.bat` 以既有 Ed25519 私鑰簽署，再於原畫面匯入簽章回應；後端會驗證簽章並以同一份本機信任清冊判定未登錄、已撤銷、單位不符或受信任。簽章不改變原 SEV 指紋，且任何 SEV 受控內容改寫後都會使簽章失效。SEV 只證明所選檔案 bytes 與 RVR 記錄相同；數位簽章另證明對應私鑰曾簽署該 SEV，但兩者都不證明文件內容或工程適用性，也不插入 PDF／DOCX 計算書正文。舊 RVR v1／v2 因未提供逐列文件 SHA-256，只能維持人工文件核對。

收到 ERH、RVR、SEV 後，可直接雙擊 `驗證SEV證據鏈.bat`，依序選取三份 JSON；若另選公開 RTB 信任清冊備份，驗證器會一併核對 RVR 與 SEV 的 Ed25519 簽章、公鑰信任及單位一致性。此流程不啟動 FastAPI、不讀取專案資料庫或私人金鑰，成功後會在 SEV 旁建立帶 `SCV-` 指紋的獨立驗證收據。工程結果通過且兩方身分均受所選 RTB 信任時，採用狀態才會是 `eligible-trusted-identities`；未提供 RTB、未簽署或信任條件不足時固定要求人工身分核對；RVR 工程結果失敗時固定不可採用。SCV 是可攜式驗證證據，不會重新計算容量，也不構成工程核可；其指紋不是 SCV 本身的數位簽章，歸檔與正式複驗時仍須保留並重新選取 SCV 所列 SHA-256 對應的來源檔。完整說明見 `SOURCE_EVIDENCE_CHAIN_VERIFIER.md`。

正式附件整理時，可把明確核可後的計算書與同批 ERH／RVR／SEV／SCV／可選 RTB 一起交給平台「正式附件包管理器」。附件檢查器會原生辨識證據種類，核對 SCV 的來源檔名、SHA-256、各層指紋、工程結果與採用狀態；缺檔、內容替換或關係矛盾固定阻擋。計算書只進入 `01_正式附件/`，全部治理 JSON 及 PDF canonical render evidence 只進入 `99_內部追溯_勿附入主報告/來源資料/`。後端端到端測試會用匿名案件實際產生核可 PDF、逐頁可見性證據、ERH／RVR／SEV／SCV／RTB，完成組包與事後驗證，並證明 OCR 證據或組包後 SEV 遭替換都會被阻擋；PDF 不以純文字層冒充可見成品證據。組包及事後驗證摘要會顯示證據鏈複驗完成數，但不會把治理資料寫入計算書；日後仍須以包內來源檔重跑獨立 Python 驗證器，附件包指紋不取代 ERH／RVR／SEV／SCV 的內容或身分驗證。

網頁可從未簽 RVR 下載具 `RSR-` 指紋的離線身分簽署請求，接收單位雙擊 `簽署RVR身分請求.bat` 選取請求與既有 Ed25519 PEM 私鑰後，即可產生簽章回應 JSON，再由網頁匯入並下載已簽 RVR。整段流程不需人工編輯 JSON；後端會重新驗證 RSR、RVR、ERH、來源計算指紋、回簽單位與簽章 bytes。私人金鑰及其密碼只由離線程序於接收單位電腦讀取，不會送進瀏覽器、API 或信任清冊。

## 規範語意追蹤

`excavation-traceability.catalog.json` 將本工具拆成 5 個可稽核面向：分析輸出匯入、支撐 / 橫擋 / 斜撐 / 大角撐檢核、柱構件與基礎承載、PDF / DOCX 報表治理、本機服務與資料治理。每一筆 trace 都需列明規範或工程判讀來源、輸入欄位、計算路線、報表落點、測試證據與人工複核邊界。

新增或修改 `.LST/.RIO/.o` parser、構件公式、柱腳 / 基礎估算、報表段落、下載 API、Excel / JSON 參考資料或啟停腳本時，請同步更新 catalog 並執行 `node excavation-traceability.contract.test.js`。若調整 PDF / DOCX 內容、latest download 流程或頁面專用閱讀狀態邊界，另需執行 `node excavation-report.contract.test.js`。若輸出依賴外部分析模型、施工圖、地質資料或專案指定值，報表與前端文字仍需保留設計者人工複核責任。

- PDF / DOCX 版面先以穩定輸出為優先，尚未完全複刻既有 Word 計算書版型
