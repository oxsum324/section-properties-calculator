# RVR／SEV 組織簽章金鑰管理

本流程用於建立、登錄、輪替與撤銷 RVR 回簽及 SEV 核驗身分共用的 Ed25519 組織金鑰。兩者使用不同簽署內容脈絡與請求種類，不能互相重播。私鑰只應存在簽署單位控制的離線電腦、加密磁碟或既有金鑰設備；網頁工具只接收公開 RKE 登錄包。

## 建立新金鑰

1. 在接收單位電腦雙擊 `建立RVR組織簽章金鑰.bat`。
2. 輸入組織名稱、金鑰名稱，選擇受保護的輸出資料夾。
3. 輸入至少 12 個字元的私鑰密碼。程式產出兩個檔案：
   - `RVR-private-RVK-....pem`：密碼加密的 PKCS#8 Ed25519 私鑰，不得交付來源端。
   - `RVR-public-enrollment-RVK-....json`：可交付來源端的公開 RKE 登錄包。
4. 私鑰與密碼應分開備份；公開 RKE 可透過案件文件或受控傳輸管道交付。

命令列亦可執行：

```powershell
python -m backend.manage_receiver_key create `
  --organization "接收單位名稱" `
  --display-name "2026 RVR 正式章" `
  --output-dir "D:\Secure\RVR-Key"
```

自動化環境可用 `--password-env <環境變數名稱>` 提供密碼，但不得把密碼寫入批次檔、版本庫或 RKE。

## RKE 公開登錄包

RKE（`receiver-verification-key-enrollment`）包含組織名稱、Key ID、公開金鑰、建立時間、選用的被取代 Key ID，以及新私鑰對登錄內容所作的 Ed25519 持有證明。來源端匯入時會重新驗證：

- 公開金鑰與 `RVK-...` Key ID 相符；
- 私鑰持有證明有效；
- `RKE-...` 包指紋與內容相符；
- 輪替時，新舊金鑰所屬組織一致。

持有證明只證明建立 RKE 的人持有對應私鑰，不能單獨證明其代表該組織。管理者仍須以電話、正式函件、既有憑證或其他獨立管道核對組織與 Key ID，並在畫面勾選確認後才能加入信任清冊。

## 本機帳號與角色

第一次開啟接收端金鑰治理區時，須由 localhost 建立第一個管理帳號。第一個帳號同時取得 `receiver-key-admin`、`receiver-key-requester`、`receiver-key-approver` 三種角色；之後由管理員建立用途分離的帳號。為相容既有帳號、備份及權限資料，角色 ID 維持不變；HTML 將後兩者分別顯示為「治理申請人」與「治理覆核人」，同時適用於金鑰輪替及到期備份處置，不應解讀為只負責單一流程。密碼須為 12 至 256 個字元，包含大寫、小寫、數字、符號中的至少三類，且不得包含登入帳號；資料庫只保存隨機鹽值與 scrypt 雜湊。

登入採 12 小時 HttpOnly、SameSite=Strict 工作階段 cookie，變更操作另須通過 CSRF token。相同帳號在 15 分鐘內連續失敗 5 次會鎖定 5 分鐘。API 只允許設定的 localhost 前端來源，不使用萬用 CORS。`receiver-key-admin` 可登錄、撤銷、備份與復原信任清冊、建立帳號，以及管理其他帳號的角色、啟用狀態與臨時密碼；治理申請人（`receiver-key-requester`）可提出金鑰輪替與到期備份處置申請；治理覆核人（`receiver-key-approver`）可覆核，但同一 operator ID 不得覆核自己的申請。

HTML 操作頁固定顯示以下唯讀治理權限矩陣；角色可以疊加，但每一角色只授與自身欄位所列權限，管理員角色不會自動取得治理申請或治理覆核權限。矩陣只供操作前核對，不會寫入 PDF／DOCX 計算書，也不取代後端逐項授權檢查。

| 角色 | 公鑰、帳號與備份治理 | 提出治理申請 | 第二人覆核 | 核心控制 |
| --- | --- | --- | --- | --- |
| 接收端金鑰管理員（`receiver-key-admin`） | 公鑰登錄／撤銷、帳號與角色管理、清冊及治理備份／復原／演練 | 須另授治理申請人角色 | 須另授治理覆核人角色 | 不得自行管理；不得停用最後一位啟用管理員 |
| 治理申請人（`receiver-key-requester`） | 不可 | 提出金鑰輪替完成及到期備份處置申請 | 不可覆核自己的申請 | 只提出申請，不撤銷舊金鑰、不移除備份；申請有效期 72 小時 |
| 治理覆核人（`receiver-key-approver`） | 不可 | 不可 | 第二人覆核輪替完成及到期備份處置 | operator ID 須與申請者不同；備份處置只做一般檔案項目移除，不代表安全抹除 |

所有矩陣所列變更操作都仍要求啟用中的登入帳號及 CSRF；帳號處於待變更臨時密碼狀態時，全部治理權限暫停。

登入後，HTML 會另顯示「目前帳號有效權限摘要」。摘要只採用後端工作階段回傳的穩定角色 ID、待變更臨時密碼狀態及身分保證邊界，將三種權限逐項標示為「有效／暫停／未授權」，不從可見按鈕或顯示姓名推測授權。若同一帳號同時具有治理申請與覆核角色，摘要仍明示後端禁止覆核自己提出的申請，雙人流程必須由不同 operator ID 完成。此摘要只供 HTML 操作頁核對，不取代後端逐項授權，也不會寫入 PDF／DOCX 計算書。

管理員登入後另顯示「治理分權健康摘要」。判定只由後端 `/api/receiver-governance-health` 產生，前端不得從帳號清單、輪替事件與備份清冊自行重建第二套健康狀態。摘要只把啟用且不處於待變更臨時密碼狀態的帳號列為有效人力，並同時檢查：（1）是否至少存在一組 operator ID 不同的有效治理申請人與治理覆核人；（2）是否存在申請／覆核角色不重疊的專責帳號組合；（3）每一筆待覆核輪替 claim 與到期備份處置 claim 是否仍有不同 operator ID 的有效覆核人；（4）SQLite 待覆核 claim 與 JSON 信任清冊事件是否缺漏、狀態或申請者 ID 矛盾。若缺少不同帳號組合，或任一待覆核 claim 不可覆核，狀態固定為「需要處理」；流程可執行但只能仰賴角色重疊帳號時顯示「可執行但角色重疊」；只有專責角色組合與全部待覆核案件覆核能力均成立時才顯示「分權完整」。目前沒有待覆核 claim 時只陳述無待覆核案件，不得解讀為曾有案件且已完成覆核。

快照追溯區固定顯示產生時間、`RGH-...` 健康摘要指紋、`ROG-...` 操作員治理來源指紋、`RTR-...` 信任清冊來源指紋與 ROE 鏈首。`ROG` 來自同一 SQLite 讀取交易中的帳號、角色、輪替 claim、到期備份處置 claim 與受驗證 ROE 鏈；`RTR` 來自另一份受驗證 JSON 信任清冊快照。兩個儲存體不是跨檔原子交易，`RGH` 只能證明這次摘要綁定所讀到的兩份來源與判定結果，不是外部可信時間戳、授權憑證或跨儲存體一致性保證。每次實際申請或覆核仍由後端重新驗證；快照回應不含帳號名稱、顯示姓名、密碼、鹽值或雜湊。摘要與追溯資訊只留在 HTML 管理頁，不會寫入 PDF／DOCX 計算書。

治理異動完成後，後端會再讀取當下兩份來源並把狀態觀測寫入 `receiver_governance_health_observations`。每一筆收據保存異動種類、不可自行填寫的 operator ID、前後狀態、數量摘要、RGH／ROG／RTR／ROE 與前序 `GHR-...`；SQLite trigger 禁止應用程式更新或刪除，單一前序索引禁止分叉，同一 RGH 重複觀測不會新增假歷程。GET 健康與歷程 API 都維持唯讀；只有治理異動、管理員 POST 登入觀測或管理員明確按下「記錄目前快照」才會追加收據。若最新收據的 RGH 與目前快照不同，HTML 必須顯示來源漂移且不得假稱目前快照已入鏈。完整歷程可匯出為帶 `GHE-...` 整包指紋的 JSON；匯出檔與鏈本身仍不是外部時間戳、數位簽章或資料庫檔案遭高權限置換時的第三方證明，也不得混入 PDF／DOCX 計算書。

管理 HTML 另提供「匯入並驗證歷程 JSON」。後端會拒絕未知欄位、前後狀態或時間不連續、收據指紋錯誤、筆數／鏈首不一致、證據邊界變更或 `GHE-...` 整包指紋錯誤；驗證只讀取上傳內容，不會合併或覆寫正式歷程鏈。

需要獨立錨定時，管理員可下載 `receiver-governance-health-checkpoint-signing-request`（`GCR-...`），以既有組織 Ed25519 私鑰在離線端執行 `簽署治理健康檢核點.bat`，產生含完整 GHE 的 `receiver-governance-health-signed-checkpoint`（`GHC-...`）。管理頁匯入後會分別顯示：密碼學簽章是否有效、Key ID 在目前信任清冊為受信任／未知／已撤銷，以及目前 GHR 與檢核點為相同、向前延伸、落後或分叉。只有「受信任簽章」且目前 GHR 相同或延伸才可顯示可錨定；落後視為疑似回溯或資料遺失，分叉亦不得接受。匯入只比對，不寫回 GHR、信任清冊或備份。

GHC 的數位簽章可防止不知道私鑰者偽造既有檢核點，但 `signedAt` 仍是簽署請求中的自陳時間，並非第三方時間戳。工具也無法知道下載檔是否確實離開本機；要抵抗資料庫、信任清冊與 v3 備份被同一高權限人員一起置換，必須把已簽署 GHC 保存在本機之外、權限與保存政策獨立的組織紀錄位置，必要時再疊加 RFC 3161、文件管理系統保留鎖或其他外部時間／不可變證據。

外部保存後不應要求原服務仍可啟動才能驗證。`驗證治理健康檢核點.bat` 可在另一台已安裝後端 Python 套件的 Windows 電腦上獨立讀取 GHC；可選 RTB 只用來判斷該公開清冊在 `exportedAt` 快照中的金鑰信任／撤銷狀態，不能反推金鑰在可自陳的 `signedAt` 已受信任；可選目前 GHE 用來比較相同、延伸、落後或分叉。工具不連接專案資料庫、不讀私人金鑰，產生的 `GCV-...` 只是一份重新驗證收據，必須連同實際 GHC、RTB、GHE 來源檔保存並可重跑，不能單獨取代來源證據。詳細操作與邊界見 `GOVERNANCE_CHECKPOINT_VERIFIER.md`。

需要第三方時間證據時，可由 `建立治理檢核可信時間請求.bat` 把已重驗 GCV 與全部來源封裝成 GAM，並產生帶 nonce、要求 TSA 憑證的 SHA-256 RFC 3161 查詢；本工具不自行選擇或連線 TSA。收到外部回應後，`完成治理檢核可信時間證據包.bat` 會用組織明確選取的信任根驗證查詢 nonce、GAM 實際 bytes 與憑證鏈，建立可由 `驗證治理檢核可信時間證據包.bat` 唯讀重跑的 GTV。TSA `genTime` 只在採用者接受該 TSA、信任根與 policy identifier 時證明 GAM 所綁內容最遲於該時已存在；工具不查 OCSP／CRL，也不證明異地保存、工程核可或正式附件資格。詳見 `GOVERNANCE_CHECKPOINT_TRUSTED_TIMESTAMP.md`。

需要外部保存端對實際入庫與保留鎖簽署負責時，可在 GTV 後建立 GAD／GAP，並要求指定 DMS／WORM 保存端回傳具物件 ID、不可變版本 ID、模式、期限及 legal hold 的 Ed25519 GAR。案件端只以組織獨立核定的公開金鑰建立 GAV；期限不足、模式不符、未啟用必要 legal hold、錯誤金鑰或內容竄改均失敗關閉。GAV 仍是保存端證言，不是保存庫現況的即時查詢，也不等於工程核可。詳見 `GOVERNANCE_TRUSTED_ARCHIVE.md`。

長期保存狀態以 GSR／GSC 週期重驗。保存端可用已輪替的現行 Ed25519 金鑰簽發 GSR，但案件端必須明確選取該公開金鑰，另附與原 GAV 來源檔及私人金鑰材料不同的當期核定證據；舊 GAR 金鑰的核定不會自動延伸到新 GSR 金鑰。詳見 `GOVERNANCE_TRUSTED_ARCHIVE_LIFECYCLE.md`。

GHR 歷程表不包含密碼資料。新版 `receiver-operator-governance-encrypted-backup` v3 會把完整 GHR 歷程與 v2 帳號治理快照一起放入 AES-256-GCM 密文，讓整個 SQLite 遺失時可在通過解密、鏈驗證與復原規則後重建正式歷程；v1／v2 舊版備份仍可讀取，但沒有來源 GHR，只會保留復原目標的本機鏈。GHE 仍是可獨立保管與重新驗證的歷程證據，不會由管理頁合併回正式鏈；GHE 與本機 v3 備份都不等於異地備援，仍需由組織另行配置受控保存與外部錨定。

帳號治理採以下失敗關閉規則：

- 管理員不得自行停用、改角色或由管理入口重設自己的密碼；須由另一位啟用中的管理員執行，避免單一工作階段自行改寫其授權證據。
- 不得停用最後一位啟用中的管理員，也不得移除其管理角色。
- 停用帳號會立即撤銷其所有工作階段；停用或撤除治理申請人（`receiver-key-requester`）角色時，該帳號尚未完成的輪替或到期備份處置 claim 同步轉為 `blocked`，不得再覆核完成。
- 管理員重設密碼會撤銷該帳號全部工作階段並標記「須變更臨時密碼」。該帳號登入後只可登出或變更本人密碼，完成後再次撤銷全部工作階段，再以新密碼登入。
- 首次建立、建立帳號、角色異動、停用／啟用、管理員密碼重設及本人密碼變更均寫入 `ROA-...`／`ROE-...` 稽核事件。SQLite trigger 禁止事件更新／刪除，並以前一事件指紋形成鏈結；這只提供本機竄改線索，不是外部可信時間戳，也不能阻止具有整個資料庫重建權限的人另建新資料庫。

稽核鏈只涵蓋升級至支援本功能後發生的帳號治理操作；升級前既有帳號不會被偽造補寫歷史事件。公開 RTB 信任清冊備份仍刻意排除帳號、密碼、工作階段、輪替 claim 與帳號治理稽核鏈；需要災難復原這些資料時，必須使用下一節的獨立加密治理備份。

這是同一服務資料庫內的本機帳號與角色驗證，不是外部組織目錄、自然人身分或公司授權的第三方證明。正式組織應由既有身分／簽核制度決定誰可取得帳號及角色，並保存帳號交付、停用與權限調整紀錄。測試或隔離部署可用 `STRUT_DB_PATH` 指向專用 SQLite 檔；正式資料庫不應與測試共用。

## 操作員治理加密備份與災難復原

已登入且具 `receiver-key-admin` 角色的帳號，可在 HTML 管理區下載 `receiver-operator-governance-encrypted-backup`。新版備份封包為 schema v3；外層只保存匯出時間、帳號／claim／事件／GHR 筆數、GHR 鏈首、scrypt 參數、AES-256-GCM nonce／salt、密文，以及 `ROG-...` 快照指紋與 `ROB-...` 整包指紋。以下內容只存在通過驗證的密文內：

- 操作員 ID、登入帳號、顯示姓名、角色、啟用狀態與建立時間；
- 隨機鹽值與 scrypt 密碼驗證值；不含任何明文密碼；
- SQLite 輪替 claim；
- SQLite 到期備份處置 claim；
- 完整 ROA／ROE 帳號治理稽核鏈。
- 完整 GHR 治理健康歷程及其 RGH／ROG／RTR／ROE 來源指紋。

登入工作階段、CSRF token 與登入失敗／限速紀錄固定不納入。每次成功匯出會先追加 `operator-governance-backup-exported` 稽核事件，因此下載檔本身也包含該次匯出的操作員與 RBE 請求識別；全新復原環境只有這類匯出事件時仍維持災難復原例外。備份密碼須為 16 至 256 個字元，只供當次請求使用，不寫入資料庫或備份檔；遺失後即無法解密。由於密文仍含可供離線猜測的密碼驗證值，備份檔必須視為高度敏感資料，與密碼分開保存，並由組織訂定存取權限、異地副本、保存期限與定期復原演練。

下載時可由管理員明確勾選另存一份受管制本機加密副本，保存期間限 1 至 365 天。副本位於服務資料庫旁的 `receiver_operator_governance_backups/managed`，以不覆寫同名檔及作業系統可用的限制權限建立。HTML 清冊不顯示伺服器路徑，且每次讀取都重新驗證加密封包、檔名所載匯出／到期時間、ROB 指紋及檔案 SHA-256；無有效副本、檔案損壞、最新有效副本仍是未涵蓋 GHR 的 v1／v2、最新 v3 副本未取得可證明 GHR 筆數／鏈首一致的 ROD v2，或對應演練超過 30 天時，健康狀態改為「需要處理」。

保存期限本身只是一項治理提醒，不會觸發自動刪除，也不得解讀為可在 SSD、雲端同步磁碟、快照或其他備份媒體上安全抹除。到期副本須由治理申請人（`receiver-key-requester`）填寫案件／變更編號與處置依據，建立 72 小時有效的 `RBR-...` claim；申請本身不改檔。之後只能由不同 operator ID 的治理覆核人（`receiver-key-approver`）覆核。後端以 SQLite 唯一未結案約束避免同一 ROB 並行申請，並將申請、覆核與完成分別追加至 ROE 鏈。

覆核通過後，後端會重新核對受管制檔名、ROB／ROG、SHA-256、匯出時間與保存期限，才從 `managed` 目錄做一般檔案項目移除，並以不覆寫方式產生 `RBD-...` 收據。完整案件與依據只留在受控 SQLite claim／ROE 鏈；RBD 只保留它們各自的 SHA-256，以及申請／覆核／完成 operator ID 與檔案指紋，避免自由文字誤帶帳號、密碼或路徑時破壞收據的隱私邊界。收據不含帳號名稱、登入密碼、備份加密密碼或伺服器路徑。若在移除、收據落地與 SQLite 結案之間中斷，claim 維持 `removal-in-progress`；已保留完成資訊時只能由同一覆核帳號續辦，避免產生不同收據。RBD 只證明該受管制目錄在結案時已無指定檔案，且明確記錄 `automaticExpiryDeletion=false`、`ordinaryFilesystemEntryRemovalOnly=true`、`secureEraseGuaranteed=false` 與 `otherCopiesMayRemain=true`。同步端、歷史備份、檔案系統快照及媒體殘留仍須由儲存管理者依組織程序處理；若需要保留法律、事故或維運證據，應在提出刪除申請前完成凍結與受控移轉。受管制本機副本仍不等於異地備份。

匯入並通過解密預覽後，可使用備份內啟用管理員帳密執行「隔離復原演練」。後端會建立暫存 SQLite、建立一次性啟動帳號、呼叫與正式復原相同的完整置換流程，再實際登入備份管理員並驗證復原事件、ROE 稽核鏈及 GHR 歷程；v3 備份的隔離復原筆數與 GHR 鏈首必須和密文內內容一致，同時比較正式治理快照前後完全一致，才會寫出 `ROD-...` v2 收據。收據只記錄 ROB／ROG／ROE／GHR／ROD 指紋、筆數、通過項目與時間，不保存帳號、登入密碼、備份加密密碼或伺服器路徑。演練證明指定密文在當時可由本版本於隔離資料庫復原，不代表外部媒體、排程、密碼保管人或完整事故應變程序已通過。

匯入檔案只會解密、驗證雙指紋與內部結構，並顯示目前／備份的帳號、事件、輪替 claim 筆數、新增或移除帳號、角色與狀態差異及備份內啟用管理員，不會立即改寫資料。執行復原同時要求：

1. 目前已登入且啟用中的管理員工作階段及有效 CSRF token；
2. 備份加密密碼；
3. 備份內一位啟用中管理員的登入帳號與實際密碼；
4. 完整置換帳號、角色、輪替 claim、備份處置 claim、稽核鏈與 v3 來源 GHR，並撤銷全部工作階段的明確確認。

既有有效治理資料庫只接受 ROE 稽核鏈及 v3 GHR 歷程都與目前相同或向前延伸，不接受舊備份回退或分叉；治理快照相同但 GHR 有合法向前延伸時仍可只為恢復缺少的歷程而執行。災難復原例外只適用於全新建立、僅有一位啟動管理員、沒有輪替／備份處置 claim，且 GHR 僅含該啟動帳號的建立、登入或備份匯出觀測。覆寫前會在 SQLite 旁的 `receiver_operator_governance_backups` 資料夾建立同密碼加密、不覆寫同名檔且含現況 GHR 的 v3 `pre-restore` 保全備份；交易取得 `BEGIN IMMEDIATE` 寫入鎖後會再次逐欄核對預覽時治理快照與 GHR，任一異動都停止並要求重新預覽。成功時原子置換治理資料與 v3 來源歷程、清除登入失敗紀錄、撤銷全部工作階段並追加 `operator-governance-restored` 稽核事件及復原後 GHR 觀測；v1／v2 則保留本機 GHR。失敗時整筆交易回滾，ROE 與 GHR 刪改鎖都保持啟用。

復原後必須用備份內管理員重新登入，核對帳號清單、輪替 claim、到期備份處置 claim、ROE 鏈首、GHR 筆數／鏈首與復原事件，並將保全檔名及指紋寫入組織事故或維運紀錄。帳號治理快照本身仍為 schema v2；加密封包為 schema v3 並納入 GHR，讀取端仍接受不含 GHR 的 v1／v2 備份，復原後帳號治理資料會由現行資料庫正規化為 v2。`pre-restore` 只在本機，不是異地備份；本功能也不提供外部可信時間戳、遠端保管、自然人身分或公司授權證明。具有資料庫或檔案系統管理權限者仍可直接替換或刪除 SQLite／備份檔，正式環境須另以作業系統權限、磁碟加密、受控備份與監測保護。操作員治理備份、清冊、演練、處置、預覽及復原資訊不是工程計算結果，不得進入 PDF／DOCX 正式計算書或公開 Pages 資產。

## 金鑰輪替

建立新金鑰時以 `--replaces-key-id RVK-...` 指定舊金鑰。來源端匯入後會保存新舊 Key ID 的輪替關聯，但登錄新金鑰不會自動撤銷舊金鑰，避免尚未完成切換的案件立即失效。同一舊 Key ID 同時只允許一把待完成輪替的受信任新金鑰，避免多條輪替路徑互相衝突。

建議順序：

1. 建立含 `replacesKeyId` 的新 RKE。
2. 來源端獨立核對並登錄新金鑰。
3. 以新金鑰完成一筆測試簽署並確認為「受信任簽章通過」。
4. 確認所有簽署端、案件與維運程序均已切換後，在新金鑰的「輪替待申請」狀態按「提出輪替完成申請」。
5. 由治理申請人（`receiver-key-requester`）填寫輪替案件或變更編號、新金鑰啟用／測試簽署／使用端切換摘要，並確認本步驟只提出申請、不撤銷舊金鑰。清冊會新增具 `RVE-...` 指紋與 72 小時期限的 `rotation-completion-requested` 事件，並保存該帳號不可變的 operator ID。
6. 由另一個 operator ID 不同的治理覆核人（`receiver-key-approver`）開啟「第二人覆核」，核對申請指紋、切換證據與變更依據，再明確確認不可復原撤銷。自己覆核、逾期、已使用、缺少 SQLite claim 或金鑰狀態已改變的申請一律拒絕。
7. 後端會再檢查新舊 Key ID 的 RKE 關聯、單位與當前受信任狀態；全部一致時才會在同一次清冊寫入中撤銷正確的舊金鑰，並保存 `rotationApprovalRequestFingerprint`、事件 `approvalRequestFingerprint`、`replacedByKeyId`、`rotationCompletionEventFingerprint` 與 `relatedKeyId` 的申請／覆核／新舊金鑰雙向追溯。SQLite 採 `BEGIN IMMEDIATE`、每把新金鑰僅一筆 pending 的部分唯一索引，以及覆核 operator ID 不得等於申請 operator ID 的資料庫 CHECK；多程序同時覆核只能成功一次。

本機帳號比自由填寫姓名更能落實角色及異人分離，但仍無法自行證明兩個帳號必然由兩位不同自然人持有，也無法證明公司授權。正式程序仍須依組織既有案件、資安或簽核系統核對。JSON 事件清冊與 SQLite claim 分屬兩個檔案，並非跨檔單一原子交易；若程序在兩次寫入間中斷，清單會把缺少 claim 的待覆核事件標示為不可核可，須先稽核事件鏈與資料庫，再於原申請失效後重新提出，不得繞過角色授權直接完成。

若舊金鑰在切換前疑似外洩、遺失或已不安全，不應等待 72 小時雙人輪替覆核，也不應為了完成一般輪替而延後撤銷；應立即使用一般撤銷流程選取實際事故原因。此時既有輪替申請會改為受阻，新金鑰標示「舊金鑰已另案撤銷，輪替關聯需人工複核」，不會偽裝成標準切換完成。

## 遺失、外洩與撤銷

若私鑰或密碼疑似外洩，應立即停止使用、通知所有來源端管理者撤銷對應 Key ID，並以全新私鑰建立輪替 RKE。撤銷不會刪除歷史記錄；舊 RVR 仍可驗證密碼學簽章，但狀態會明確顯示公鑰已撤銷，不得再視為受信任回簽。

撤銷時必須在「本機受信任回簽公鑰」填寫：

- 原因分類及具體處理摘要；
- 實際處理者；
- 事故、案件或變更編號（如有）；
- 不可復原確認。

成功撤銷後，原始原因不得由畫面重複撤銷或覆寫。工具會把登錄與撤銷寫入 `receiver-verification-key-event` 清冊，每筆事件包含 `RVE-...` 指紋及前一筆事件指紋，以偵測內容遭修改或事件次序中斷。這是本機稽核完整性線索，不是外部可信時間戳、憑證機構簽章或防止具有檔案權限者重建整份清冊的安全保證；正式事故仍應同步保存於組織既有案件或資安紀錄。

建議處理順序：立即停用私鑰、撤銷所有來源端的 Key ID、保存事件編號與通知證據、建立全新輪替 RKE、完成測試簽署，再依組織程序結案。不得為了恢復受信任狀態而修改舊撤銷事件；誤撤銷時也應建立新金鑰，不應復活舊 Key ID。

## 信任清冊備份與復原

「接收端回簽助手」可下載 `receiver-verification-trust-registry-backup` JSON。備份只包含公開金鑰、登錄資料與生命週期事件，不包含私鑰、私鑰密碼或其他秘密；但它仍揭露組織採信關係與事故處理紀錄，應納入案件或組織的受控備份，不宜公開散布。

每份備份同時保存：

- `RTR-...` 清冊指紋：固定金鑰及事件快照；
- `RTB-...` 備份指紋：再固定匯出時間與完整備份包；
- 金鑰／事件筆數與事件鏈尾指紋，供匯入時交叉驗證。

復原採「先驗證、後預覽、再明確核准」三階段。匯入不會立即改動本機檔案；畫面先列出新增、移除、狀態變更與目前清冊狀態。核准復原前，後端會再次驗證整包內容，並在同一資料夾建立 `pre-restore` 保護副本。復原是完整快照置換，不做不透明的欄位合併。

當目前清冊有效時，只允許事件鏈向前延伸：不得移除既有 Key ID、改寫既有登錄資料、回退事件鏈，或把已撤銷金鑰恢復為受信任。只有目前清冊遺失或已損毀、無法驗證時，才可由已通過雙重指紋與事件一致性檢查的備份進行災難復原。復原完成後仍應以備份指紋、保護副本與組織案件紀錄交叉確認；本工具不提供外部可信時間戳、遠端備份保管或憑證機構背書。

信任清冊備份與復原屬治理工作區，不是計算結果，也不得插入 PDF／DOCX 正式計算書正文。

### 離線備份與復原演練

Windows 使用者可雙擊 `備份與演練RVR信任清冊.bat`，選擇組織控制的備份資料夾。預設 `Cycle` 流程會：

1. 從正式清冊建立新的公開資料備份，落地後立即回讀並重驗 `RTB-...`、`RTR-...` 與事件鏈；
2. 在作業系統暫存目錄建立隔離清冊，實際執行一次完整復原；
3. 比對復原後 `RTR-...`、金鑰與事件筆數；
4. 再次確認正式清冊 SHA-256 未變動；
5. 產生具 `RDR-...` 指紋的 `receiver-trust-registry-recovery-drill-receipt` 通過收據。

若備份內容遭修改、正式清冊無法讀取、備份超過新鮮度門檻、檔名碰撞、隔離復原不一致，或正式清冊在演練期間發生異動，流程會停止且不產生通過收據。工具不覆寫同名備份，也不自動刪除歷史檔案。

排程環境可直接執行 PowerShell，不要使用會等待按鍵的 `.bat`：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "C:\Path\開挖擋土支撐\backup_receiver_trust_registry.ps1" `
  -Mode Cycle `
  -OutputDirectory "X:\受控備份\RVR信任清冊" `
  -MaxAgeDays 30
```

建議把輸出目錄設在與正式清冊不同的受控磁碟、受管網路位置或組織既有備份系統，並由組織決定保存年限、存取權限、異地副本及定期抽驗。`RDR-...` 只證明該次備份曾在隔離暫存清冊成功復原且正式清冊未被該流程更動，不等於外部可信時間戳、異地副本存在證明或正式工程核可。

### 備份健康監測

Windows 使用者可雙擊 `檢查RVR備份健康狀態.bat`，或讓工作排程器執行 `check_receiver_trust_backup_health.ps1`。健康檢查會同時驗證最新 `RTB-...` 備份、最新 `RDR-...` 收據、兩者的檔名／SHA-256／指紋關聯、新鮮度，以及每週備份排程最近一次結果。任何一項不符都會寫入 `RVR-backup-health-latest.json`，並可用 `-ShowAlert` 顯示限時警示；檢查本身不會修改正式清冊、備份或演練收據。

健康狀態或受控問題代碼改變時，備份資料夾會新增 `RVR-backup-health-event-...-RBH-....json`。每筆事件都含前筆事件指紋並重新驗證串鏈；同一狀態與同一組問題代碼的每日檢查只更新 latest，不重複新增事件。`-ShowAlert` 同步採轉換節流：首次異常或問題種類改變時顯示警示，從異常恢復正常時顯示恢復通知；相同異常仍讓排程回傳失敗，但不會每天重複彈窗。若歷程無法驗證或寫入，健康檢查會加入 `history-record-failed`、每次警示並以失敗代碼結束，避免節流掩蓋稽核故障。

本機儀表板另以 `DashboardStatusMaxAgeHours` 判定摘要是否仍可代表目前狀態，預設為 36 小時，容許每日排程因休眠或開機時間略有延遲。超過門檻時，儀表板會加入只存在於閱讀層的 `health-check-stale` 並撤銷健康綠燈，提示檢查每日健康排程；因產生摘要的排程本身已漏跑，這項閱讀層判定不會偽造新的 RBH 事件。下一次排程成功後會以新摘要自動恢復。

每週備份排程若為七天一次，健康檢查建議每天執行並把 `-MaxAgeDays` 設為 `8`，保留合理的登入與同步時間差：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File "C:\Path\開挖擋土支撐\check_receiver_trust_backup_health.ps1" `
  -BackupDirectory "X:\受控備份\RVR信任清冊" `
  -BackupTaskName "RVR信任清冊每週備份與復原演練" `
  -MaxAgeDays 8 `
```
