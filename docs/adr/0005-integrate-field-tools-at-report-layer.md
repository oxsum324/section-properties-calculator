# ADR-0005：現場鑑定工具的「一條龍」整合方式

## 背景

三個現場工具已各自可用，使用者的下一個目標是「把現況鑑定的整個附件做成一份完整的報告輸出」。2026-09-30 決定傾斜測量先與現況鑑定分開、「等較成熟之後再做一條龍的主機平台」。本 ADR 決定整合要放在哪一層。

### 作用力

1. 單人開發：使用者裁定、Claude 寫派工與核對、Codex 實作；三個 repo 可同時各派一條分支。
2. 現況鑑定在主 repo，受全站發布閘門約束（完整預檢約 50 分鐘、證據 commit）；兩個測量工具合併即上線。
3. 2026-09-30 已明確採「複製後獨立演進」（B 方案），複製品一個月內已分歧。
4. 資料只能存在本機瀏覽器與使用者匯出的案件檔，公開 Pages 不得含私人資料。
5. 三工具的實機驗收尚未全部完成（傾斜測量三個停止點待驗收）。
6. 最終使用情境是報告附件：封面、目錄、各節（損壞紀錄與照片、水準、傾斜）、頁碼、簽認。

## 考慮的選項

### 選項 A：資料層整合 —— 維持三工具，新增「鑑定附件彙整器」（採納）

第四個離線工具（獨立 repo，比照測量工具部署）。讀入三種案件檔，依「共同案件識別頭」對齊案號與戶別，產出一份完整附件（封面、目錄、各節、連續頁碼）。三工具只需（1）補共同識別頭的選填欄位或對映，（2）維持各自附件節輸出的穩定格式。

| 面向 | 評估 |
|---|---|
| 複雜度 | 中：彙整器本身是新工具；三工具改動極小 |
| 對現有 repo 影響 | 低：不改 schema、不改發布方式 |
| 時程 | 可分期：先只彙整現況鑑定＋傾斜，再加水準 |
| 風險 | 中：跨工具 PDF 合併與頁碼需設計（見取捨） |
| 可逆性 | 高：彙整器失敗不影響三工具 |
| 與派工模式適配 | 高：一個 repo 一條分支 |

**優點**：不碰已上線工具；三種案件檔都是自描述、含媒體的離線格式，彙整器只需唯讀消費；可作為選項 B 的前置（共同識別頭與附件節介面就是未來合併 schema 的核心）。
**缺點**：repo 增為四個；共用程式分歧持續（需定期差異稽核）；使用者要在四個工具間匯出匯入。

### 選項 B：程式碼層整合 —— 單一整合 App

新 repo，一個 PWA 含三模組，共用 store、annotation、exif、強光、sw，單一案件檔。

| 面向 | 評估 |
|---|---|
| 複雜度 | 高：合併 schema 18／1／1，重寫三套 UI 流程與測試 |
| 對現有 repo 影響 | 高：三工具同時凍結或雙軌維護 |
| 時程 | 長：至少數個版本週期，期間現場無新功能 |
| 風險 | 高：實機驗收未完成就重寫；單一發布閘門影響三工具 |
| 可逆性 | 低 |
| 與派工模式適配 | 低：單一 repo 的大改動難以切成可核對的小 PR |

**優點**：最終型態最乾淨，使用者只有一個工具與一個案件檔。
**缺點**：成本與風險集中；與作用力 2、3、5 衝突。

### 選項 C：共用核心套件 —— 先抽 survey-core，再談彙整

抽出 exif、integrity、sw、強光、標註幾何為獨立套件，三工具逐步改用；彙整器之後再做。

| 面向 | 評估 |
|---|---|
| 複雜度 | 中高：跨 repo 版本同步（submodule 或複製腳本） |
| 對現有 repo 影響 | 中：三工具都要改 import 與測試 |
| 時程 | 先付成本、後見效益；對「完整報告輸出」沒有直接貢獻 |
| 風險 | 中：與 9-30 的 B 方案決定相反；無團隊共享維護時收益有限 |
| 可逆性 | 中 |
| 與派工模式適配 | 中：每次核心升版要三個 repo 各開 PR |

**優點**：止住分歧。
**缺點**：使用者價值延後；三份複製品差異目前都在百行內，分歧成本尚可承受。

## 取捨分析

- 「一條龍」的使用者價值在**報告彙整**，不在程式碼合併。選項 A 直接對準價值；B、C 先付整合成本。
- 三種案件檔已是穩定的交換格式（含媒體、含指紋），資料層整合有現成基礎；程式碼層整合則要先解決 schema 與治理差異。
- 共用程式分歧是真實成本，但目前規模（三檔、各百行內）可用「每次升版做一次差異稽核、只回補安全或正確性修正」控制，不需為此重構。
- 選項 A 最難的一點是**跨工具的頁碼與 PDF**：html2pdf 產出的是影像式 PDF，現況鑑定走系統列印。可行做法是彙整器以「單一 HTML 列印文件」組稿（各工具提供 A4 樣式的 HTML 節，彙整器加封面、目錄、頁碼），由系統列印產出一份向量 PDF；不做 PDF 檔案合併，避免引入新的第三方套件。此點在彙整器的設計文件再定。
- 選項 A 不排除日後走向 B：當三工具都成熟、實機驗收完成、且四工具間的匯出匯入成為主要痛點時，再以 A 已定義的識別頭與節介面為基礎合併。

## 決定

採**選項 A**，並先定兩個約定（不升 schema，只加選填欄位或對映）：

1. **共同案件識別頭**：欄位與三工具對映見附錄 A。
2. **附件節輸出介面**：各工具可匯出「自包含的 A4 列印 HTML 節」（內嵌樣式與影像、不含腳本、頁碼留給彙整器），彙整器只負責排序、封面、目錄、頁碼與交叉引用。介面細節在彙整器設計文件定義。

彙整器為獨立 repo（獨立部署、資料只在本機），第一版範圍先限現況鑑定＋傾斜兩種輸入。

## 後果

- **變容易**：三工具維持各自節奏與派工；彙整器可獨立驗收；任何一環失敗都不影響其他工具。
- **變困難**：四到五個 repo 的版本矩陣；使用者現場需多一次匯出匯入；共用程式持續分歧需稽核。
- **需再回頭看**：（1）現況鑑定是否遷出主 repo 改為獨立部署；（2）彙整器的 PDF 策略若系統列印不可行；（3）當匯出匯入成為主要痛點時是否進入選項 B。

## 附錄 A：共同案件識別頭

| 彙整器鍵 | 意義 | 現況鑑定紀錄 | 水準測量紀錄 | 傾斜測量紀錄 |
|---|---|---|---|---|
| `caseNumber` | 鑑定案編號（公會案號或委託案號，選填） | 待新增選填 `caseNumber`（2026-10-24 裁定，見行動項 3）；`code` 維持案件代號，不假設等於公會案號 | `number` | `header.caseNumber` |
| `householdNo` | 戶別／住戶編號 | `units[].code` | 新增 `householdNo`（V0.7.6） | `header.householdNo` |

| `orgName` | 鑑定單位／公會／委託人（選填） | 待新增選填 `orgName`（2026-10-24 裁定，見行動項 3） | 新增 `orgName`（V0.7.6） | `header.orgName` |
| `surveyDate` | 會勘／測量日期 | `date`（案件）、`visits[].start`（各次會勘） | `date` | `header.surveyDate` |
| `caseName` | 案件名稱（顯示用） | `name` | `name` | 無（以 `caseNumber` 為主） |

規則：
- 全部為選填；缺值時彙整器以「未填」顯示，不阻擋彙整。
- 2026-10-24 使用者裁定：識別頭不綁公會案號。不論由哪個公會或委託人指派，或由本公司自行作為附件表頭，各欄位都可有可無；各工具以「是否套用附件表頭」勾選加各欄位留白表達，留白欄位不列印、不入案件指紋（比照水準測量 V0.7.6 的空字串過濾）。
- 對齊鍵為 `caseNumber`＋`householdNo`；水準測量為全棟量測時 `householdNo` 留空，彙整器視為「全案共用節」。
- 各工具保留原有欄位名稱，不改既有 schema；彙整器端做對映。
