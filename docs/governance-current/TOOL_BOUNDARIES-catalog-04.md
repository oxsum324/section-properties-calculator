拆撐承接構造交接 JSON 屬跨工具／專案資料交接，不是正式計算書內容。後端僅可從最新重算結果建立，且只納入來源構件非 NG、拆撐生命週期與人工處置完整的列；檔案須保存來源計算指紋、逐列 ERT 指紋、整包 ERH 指紋，以及 `pending`、`autoApplied=false`、`autoVerified=false` 邊界。已發 ERH 版本須保存於專案。獨立接收端回簽助手只可在 ERH／ERT 指紋驗證成功後展開逐列表單，並由後端以受控欄位、自動彙整、固定責任邊界及 RVR 指紋產生回簽；它只能記錄接收端依正式模型完成的結果，不得自行推導容量、傳力方向、分配、偏心或載重組合。接收端回傳的 `receiver-capacity-verification-receipt` 只可在 RVR 指紋、來源計算指紋、ERH／ERT 關聯、逐列完整涵蓋、容量利用率與彙整結果均一致時匯入。ERH／ERT／RVR 指紋只證明內容完整性；既有未簽 RVR 必須維持人工核對身分。附加 Ed25519 簽章時，驗章須綁定 RVR、ERH、來源計算指紋、回簽單位及簽章時間，且 RVR 指紋不得因附加簽章改變。自帶公鑰只能證明簽章在密碼學上有效，不能自行取得信任；只有管理者已核對並登錄本機信任清冊、未撤銷且單位相符的公鑰，才可顯示「受信任簽章通過」。私人金鑰不得由網頁工具產生或保存；未知、撤銷、單位不符或未簽狀態均不得自動顯示為正式工程核可。

RVR 離線簽署介接必須以具獨立 `RSR-` 指紋的簽署請求固定實際 Ed25519 bytes；簽章回應須攜回完整請求及公開簽章資料，且在附加到 RVR 前重新核對 RSR、RVR、ERH、來源計算指紋與回簽單位。網頁及 API 不得接收私人金鑰或私鑰密碼。離線簽署程式只可讀取使用者明確選取的既有 Ed25519 私鑰，輸出不得包含私人金鑰或密碼，也不得把簽章有效直接提升為公鑰受信任或工程核可。

RVR 組織建鑰只可在接收單位控制的本機或金鑰設備執行；公開 RKE 的私鑰持有證明不等於組織身分證明。來源端登錄信任前須明確確認已透過獨立管道核對組織與 Key ID；`replacesKeyId` 只保存輪替關聯，不得自動撤銷舊金鑰。同一舊金鑰只得有一把仍受信任的待完成輪替新金鑰。所有信任清冊變更須由本機登入帳號執行：密碼只保存 scrypt 雜湊，工作階段採 HttpOnly／SameSite=Strict cookie 並以 CSRF token 保護，登入須限速，API 不得開放萬用 CORS；管理、申請與覆核角色須分開授權。帳號停用、重新啟用、角色異動、管理員密碼重設及本人密碼變更須以 SQLite 交易寫入禁止 UPDATE／DELETE 的串接指紋稽核事件；不得自行停用、改角色或由管理入口重設自己的密碼。停用或撤除申請角色須將該帳號尚未完成的輪替 claim 改為 blocked；停用與密碼重設須撤銷既有工作階段，管理員重設後須強制本人先變更臨時密碼，始得執行其他權限操作。輪替完成必須分成兩筆事件：具申請角色的帳號提出具 RVE 指紋、必填變更編號、切換摘要與 72 小時期限的申請；具覆核角色且 operator ID 不同的帳號另行確認後，專用 API 才可重驗新舊金鑰關聯、同單位與當前受信任狀態，並在同一次清冊寫入中撤銷正確舊金鑰。SQLite 須以 `BEGIN IMMEDIATE`、每把新金鑰僅一筆 pending 的部分唯一索引及申請／覆核 operator ID 不同的 CHECK 約束跨程序競爭。完成事件須保存兩個 operator ID，並以 `rotationApprovalRequestFingerprint`、`approvalRequestFingerprint`、`replacedByKeyId`、`rotationCompletionEventFingerprint` 及 `relatedKeyId` 建立雙向追溯；缺少 SQLite claim 的還原或舊版待審事件不得由角色權限核可。一般撤銷與舊版直接完成 API 不得以「輪替完成」原因繞過兩階段流程。本機帳號只驗證同一服務資料庫內的帳號、角色與工作階段，不等於外部組織目錄、自然人身分或公司授權已由第三方驗證。帳號稽核鏈僅涵蓋功能啟用後的治理操作，且不是外部可信時間戳；公開 RTB 不包含帳號、工作階段、輪替 claim 或帳號稽核鏈。JSON 事件清冊與 SQLite claim 分屬兩個檔案，不得宣稱跨檔單一原子交易；中斷或狀態矛盾時須失敗關閉並人工稽核。疑似外洩、確認外洩或私鑰遺失的緊急撤銷不得因雙人輪替門檻而延誤。

RVR 操作員治理災難復原必須使用獨立的 `receiver-operator-governance-encrypted-backup`，不得以只含公開資料的 RTB 代替。新版封包為 schema v3；帳號、角色、加鹽密碼驗證值、輪替 claim、到期備份處置 claim、ROE 稽核鏈與完整 GHR 治理健康歷程只可存在 scrypt 衍生金鑰的 AES-256-GCM 密文內。外層只可揭露時間、筆數、GHR 鏈首、加密參數與 ROB／ROG 指紋，且工作階段、CSRF token、登入失敗與限速紀錄不得備份；讀取端仍須接受不含 GHR 的 v1／v2 備份。匯出前須先追加匯出 ROE 與對應健康觀測，使 v3 密文內最新 GHR 綁定該次治理快照。匯出、清冊、演練、預覽與復原 API 均須要求已登入的啟用中 `receiver-key-admin`，所有變更或解密動作另須 CSRF；復原另須通過備份密碼、備份內啟用管理員帳密及完整置換確認。下載時另存受管制本機副本必須明確 opt-in，保存期間限 1 至 365 天；清冊須逐檔重驗封包、檔名、時間、ROB 指紋與 SHA-256，顯示是否涵蓋 GHR、筆數與鏈首，且無有效副本、檔案無法驗證、最新副本未演練或同一副本的演練超過 30 天均不得顯示健康。演練必須在隔離暫存 SQLite 使用實際復原函式，驗證備份管理員登入、復原事件、ROE 及 GHR 鏈；v3 歷程筆數與鏈首須完全一致，並以正式治理快照前後相同作為 `ROD-...` v2 通過收據前提。收據不得保存帳號、密碼、加密密碼或伺服器路徑。保存期限本身只提供治理提醒，不得觸發自動刪除。到期副本須先由啟用中 `receiver-key-requester` 建立含案件與依據、72 小時有效且同一 ROB 唯一未結案的 `RBR-...` claim，再由不同 operator ID 的 `receiver-key-approver` 覆核；覆核後須重新驗證受管制檔案及 SHA-256，才可做一般檔案項目移除並以不覆寫方式寫出 `RBD-...` 收據。申請、覆核與完成須分別追加 ROE 事件；中斷狀態須可由已保留完成資訊的同一覆核帳號續辦，且 claim 與事件須隨治理備份復原。RBD 必須明示 `automaticExpiryDeletion=false`、`ordinaryFilesystemEntryRemovalOnly=true`、`secureEraseGuaranteed=false`、`otherCopiesMayRemain=true`，不得宣稱 SSD、同步端、快照或其他備份媒體已安全抹除；收據不得含帳號名稱、密碼、加密密碼或伺服器路徑。既有有效資料庫只允許 ROE 與 GHR 都相同或向前延伸；全新單一啟動管理員且無輪替／備份處置 claim、GHR 只含啟動／登入／匯出觀測時才可作災難復原例外。v1／v2 復原須保留本機 GHR，不得宣稱恢復來源歷程。寫入前須建立同密碼加密、不覆寫且含現況 GHR 的 v3 pre-restore 保全檔，並在 `BEGIN IMMEDIATE` 交易內確認治理快照與 GHR 均仍等於預覽現況，再原子置換治理表及 v3 來源歷程、清除登入失敗、撤銷全部工作階段、追加復原 ROE 與復原後 GHR；競爭異動或任一步失敗均須整筆回滾並保持兩條鏈禁止 UPDATE／DELETE。備份密碼不得保存，密碼遺失即不可復原；因密文含加鹽密碼驗證值，檔案仍須以高度敏感資料受控並與密碼分開。受管制本機副本與 pre-restore 都不等於異地備份；應用層控制不能阻止具檔案或資料庫管理權限者直接替換或刪除資料，也不是外部可信時間戳、組織身分或工程核可。治理備份、清冊、演練、處置、差異與復原結果不得進入 PDF／DOCX 計算書或公開 Pages。

`receiver-key-requester` 與 `receiver-key-approver` 是既有帳號、備份及權限資料的相容性契約，不得因顯示文字調整而變更。HTML 顯示名稱固定為「治理申請人」與「治理覆核人」，兩者同時涵蓋金鑰輪替及到期備份處置，不得以只暗示單一流程的名稱縮限職責。HTML 必須提供唯讀治理權限矩陣，逐列列出 `receiver-key-admin`、`receiver-key-requester`、`receiver-key-approver` 單獨授權時可執行的管理、申請、覆核動作及異人限制，並明示角色可疊加但管理員角色不自動取得其他兩種權限。登入後另須只依後端工作階段回傳的穩定角色 ID 與待變更臨時密碼狀態產生目前帳號有效權限摘要，逐項區分有效、暫停及未授權；兼具申請與覆核角色仍須提示後端禁止自我覆核。管理員可見的治理分權健康摘要必須由後端單一唯讀 API 判定，前端不得自行拼接帳號、信任清冊與處置清冊形成第二套權威。後端只能把啟用且無待變更臨時密碼的帳號列為有效人力，須檢查不同 operator ID 的申請／覆核組合、專責角色分離、每筆待覆核輪替／備份處置 claim 的合格第二人，以及 SQLite claim 與 JSON 信任清冊事件的缺漏或矛盾；缺少不同帳號組合或任一 claim 不可覆核時必須顯示需要處理，角色重疊但可執行時不得宣稱分權完整。回應須提供 `RGH` 健康摘要、`ROG` 帳號治理快照、`RTR` 信任清冊及 ROE 鏈首追溯指紋，但不得含帳號名稱、顯示姓名、密碼或密碼驗證資料；並須明示 SQLite 單一讀取交易與 JSON 單一驗證快照不是跨儲存體原子交易，所有實際操作仍重新授權。每次治理異動後須以 append-only 收據鏈保存狀態轉換、來源指紋與前序 `GHR`；GET 不得因查看而寫入，重複 RGH 不得膨脹歷程，來源漂移未入鏈時須明示且只能由管理員 POST 觀測補記。完整歷程 JSON 須具 `GHE` 整包指紋並揭露其不是外部時間戳、數位簽章或高權限資料庫置換防護。矩陣、摘要、追溯與歷程資訊只供操作前核對，不得取代後端逐項授權，也不得進入 PDF／DOCX 計算書或公開 Pages。

RVR 信任金鑰撤銷是一次性且不可由畫面覆寫的治理事件。撤銷 API 必須要求受控原因分類、具體摘要、處理者、選用的事故／案件編號及不可復原確認；清冊同時保存金鑰撤銷欄位與串接前一事件指紋的 `receiver-verification-key-event`。重複撤銷、缺少確認、非法原因分類或事件指紋／順序不符必須失敗關閉。`RVE-...` 只提供本機完整性稽核線索，不得宣稱為外部可信時間戳或憑證機構背書。

RVR 信任清冊備份必須只含公開金鑰、登錄資料與生命週期事件，不得含私人金鑰、密碼或秘密欄位；匯出須以 `RTR-...` 固定清冊快照並以 `RTB-...` 固定完整備份包。匯入只可先驗證及產生差異預覽，不得立即改動本機清冊。復原 API 必須要求明確確認、寫入前建立 `pre-restore` 保護副本並在寫入後重驗清冊指紋。當目前清冊有效時，只允許既有事件鏈的向前延伸；移除既有 Key ID、改寫既有登錄／撤銷紀錄、回退事件鏈或逆轉撤銷均須失敗關閉。只有清冊遺失或無法讀取時，才可由通過完整驗證的快照進行災難復原。備份不等於外部可信時間戳、遠端保管或憑證機構背書，且不得出現在 PDF／DOCX 計算書正文。

RVR 定期備份演練只能在隔離暫存清冊執行真實復原；產生 `receiver-trust-registry-recovery-drill-receipt` 前，必須驗證備份雙指紋、事件鏈、選用的新鮮度門檻、復原後清冊指紋與筆數，並證明正式清冊前後 SHA-256 不變。`RDR-...` 收據必須固定備份檔 SHA-256、RTB、RTR、演練時間與結果；備份遭竄改、同名檔案已存在、隔離復原不一致或正式清冊發生異動時須失敗關閉且不得產生通過收據。工具不得自動覆寫或刪除歷史備份；RDR 不得宣稱為外部時間戳、異地副本證明或工程核可，也不得進入正式計算書正文。

RC 梁、柱、板、牆、剪力牆、基礎與單樁的專案 JSON 維持來源資料角色，附件檢查器直接辨識既有 `metadata`／`fields` 與單樁 `state` 結構。七個 RC 計算書的產出工具名稱與版本須和各自專案 JSON 完全一致，讓案件、工具、版本及 `CF-` 可形成自動來源／報告配對；包內同時存在完整追溯來源與正式計算書時至少須形成一組完整配對，零配對必須 `blocked`。實際瀏覽器測試必須把核可後可攜 HTML 與真實專案 JSON 交給同一組包檢查器，並證明正常配對 `ready`、竄改指紋、錯版本及完整身分改寫來源 `blocked`。不得要求使用者另造轉接 JSON，也不得把專案來源移入正式附件目錄。
